# 多 Agent 协作规约（dsh + codex + qoder）

> 建立于 2026-08-31 · 由用户确认生效 · 参考 clear-jlpt-n2 协作模式、按本仓库约束适配

本文是 dsh（监督）、codex（实现者）与 qoder（方案建议/初审）在本仓库协作的唯一规约。
其他文档只链接本文，不复制规则。

## 一、角色分工

| 角色 | 职责 |
|------|------|
| 用户 | 提出要求、最终拍板；确认规约变更与重大决策 |
| dsh（监督） | 把要求整理成自包含提示词与验收标准；细化方案并决定是否采纳 qoder 建议；终审 codex 成果、给出裁决与问题清单；按 §七 执行提交并复核门禁（提交决定权归作者，§九）；维护审查结论与轮次索引 |
| codex（实现者） | 按提示词落实实现，交付可运行成果；有主动性：可提出更优方案、发现问题主动汇报 |
| qoder（方案建议/初审） | 顾问角色：对 dsh 细化后的方案提建议与优化；对 codex 产出做初审（逐项核验 + 问题分级）；无实现权、无提交权，建议由 dsh 裁定、用户拍板 |

## 二、标准流程（每轮迭代）

1. 用户向 dsh 提出要求，并声明 qoder 状态（"qoder在"/"qoder不在"，未声明默认跳过，
   见 §九）→ dsh 创建轮次 `collab/R{编号}-{YYYY-MM-DD}-{主题}/`，同时写入：
   - `request.md`：用户要求原文 + 完整提示词（本机私有目录，见 §五；凭据/密钥禁入），
     含本轮 qoder 状态声明；
   - `report.md` 模板：固定节标题（做了什么/产出文件清单/验证结果/偏差及原因/遗留问题），
     状态占位 `待开发`；
   - 在 `collab/INDEX.md` 登记该轮（状态 `待开发`）。
2. qoder 参与时：dsh 把细化方案交 qoder 提建议与优化（写入同目录
   `qoder-notes.md`「方案建议」节），dsh 采纳或否决后定稿提示词。
3. 用户将提示词交给 codex 执行；codex 如有更优方案可主动提出，经确认后执行。
4. codex 完成后填充同目录 `report.md`（做了什么、产出文件清单、验证结果、与提示词的
   偏差及原因、遗留问题），并把 INDEX 状态更新为 `待审查`。
5. qoder 参与时：对 codex 产出做初审——对照验收标准逐项核验并独立复核关键声明，写入
   `qoder-notes.md`「初审结论」节（问题分级 P1/P2/P3 + 证据）→ dsh 终审
   （可采纳或推翻 qoder 结论）→ 问题清单写入 `report.md` → codex 返工或通过。
6. 审查通过后按本仓库 git 纪律提交（见 §七），提交说明由用户/监督定稿。

## 三、提示词规范（dsh 产出）

- **自包含**：写明背景、目标、具体任务、验收标准、约束，codex 无需追问即可执行。
- **明确边界**（三层，按此分级写入提示词）：
  - **绝对禁止**（任何情况下不可修改）：本地载荷 `debs/`、`vendor/`、`build/`、
    `third_party/`，以及监督分支 `migration/supervised-source-tree`。
  - **默认保护**（默认不可修改；仅当用户在提示词中明确批准**精确路径范围**后才可改）：
    `drivers/`、`baselines/`、`binary-manifest.json`。
  - **自由范围**：其余文件，但须遵守仓库门禁（见 §六）。
- **明确交付物**：文件路径、格式、登记要求（新脚本/测试需同步 scripts/README、tests/README、
  test-strategy 与 project-tools allowlist）。
- 验收标准给足，但不限制实现路径；鼓励 codex 主动提出更优方案。

## 四、codex 主动性（实现者权限与义务）

- 收到提示词后，若认为有更优方案（工具选型、分批策略、产出结构等），可主动提出替代方案并
  说明理由，经确认后执行。
- 执行中发现提示词有误、素材缺失、或需求与实际冲突，主动汇报，不闷头硬干。
- 遇阻塞或重大偏差，及时汇报进展与影响面。
- 汇报内容须包含：做了什么、产出文件清单、验证结果、与提示词的偏差及原因、遗留问题。

## 五、合作目录存档（`collab/`）

- 位置：仓库根目录 `collab/`（英文目录名；唯一外层目录，所有轮次子目录收于其下，根目录不
  散放）。**本机私有目录**：已加入 `.gitignore`，不上传 GitHub、不参与任何公开分发。
- 结构：`collab/R{编号}-{YYYY-MM-DD}-{主题}/`，创建轮次时即含 `request.md`（用户要求原文 +
  dsh 提示词，本机私有）与 `report.md` 模板（codex 汇报 + dsh 审查结论）、可选附加 `.md`
  交付物；qoder 参与轮次含 `qoder-notes.md`（方案建议 + 初审结论）；**轮次目录内只允许
  Markdown 文件**（禁止二进制、代码快照等非约定文件，机械强制）。
- 索引：`collab/INDEX.md` 记录每轮 轮次/日期/主题/状态（状态 ∈
  待开发/开发中/待审查/通过/返工/已提交/执行中），与轮次目录按编号**双向一一对应**。
- **许可与发布边界**：`collab/` 本机私有、不入 Git，因此不是公开分发面；仍**排除出
  project-tools 候选制品**（denylist `^collab/` 防御性保留），不自动认定任何许可证；
  轮次记录中**不得出现凭据、token、私钥或机器身份**（隐私扫描覆盖 collab/），其他信息
  可按需保存；任何内容若要离开本机（同步到文档、贴出汇报等），必须先脱敏并经隐私审查。
- 机械校验：目录命名（`R{编号}-{日期}-{主题}`）、编号唯一、request.md/report.md 齐全（模板
  在创建时即生成）、INDEX 登记与合法状态、仅 Markdown 文件、INDEX 与目录按编号**双向一一对应**
  （精确匹配编号、日期与主题，R01 不误配 R010；重复行/孤立行/孤立目录/根目录或内部符号链接/
  嵌套目录均拒绝；INDEX 与隐藏 Markdown 同样纳入大小写无关的隐私扫描），由
  `tools/validate-collab.py` 执行、`scripts/check-docs.sh` 强制（collab/ 不存在时视为无轮次，
  直接通过）；fixture 见 `tests/unit/run-collab-structure-tests.sh`。

## 六、审查标准与仓库门禁（本仓库专属）

- [ ] 验收标准逐条核对通过。
- [ ] 无越界改动：§三 的绝对禁止项零改动；默认保护项仅在用户批准的精确范围内改动。
- [ ] **CI/沙箱测试入口**全部 PASS，且 test-strategy.md 计数与实际一致（"全部测试入口"指
  test-strategy.md 列出的 CI/沙箱入口，不含需真实设备/root/副作用的 runtime/授权测试；后者仅当
  任务需要且用户在提示词中批准时运行）。文档-only 任务可按风险运行相关测试 + 固定门禁。
- [ ] `python3 tools/audit-licenses.py` → `license_audit_overall=PASS` 且
  `license_release_gate=BLOCKED` 保持（发布决策 1C）。
- [ ] `bash scripts/check-docs.sh` → `RESULT: PASS_DOCS`。
- [ ] `git diff --cached --check` 干净；隐私扫描无真实用户名/hostname/凭据/token/私钥/本机
  绝对路径泄漏；涉及 shell 时 `bash -n` 与 ShellCheck（error+warning）清零。
- [ ] 新增 tracked 文件已同步 allowlist（`--write-allowlists`）与文档登记；无未登记脚本/工具。

## 七、git 纪律（本仓库与参考项目不同）

- 本仓库默认**停在提交前**：dsh 与 codex 的产出均**不得自行 commit**。
- commit / push 以作者提交决定为前提（§九 提交决定）；dsh 作为最终评审，发现
  问题可要求作者修改后再提交；dsh 执行 git 操作前做机械门禁复核并记录；用户
  最终拍板可推翻任何提交决定；**不创建 tag/Release**（发布决策 1C：当前不发布）。
- 每轮产出的报告必须明确仓库内产出的 staged / unstaged / untracked 状态与 HEAD/领先关系
  （collab/ 本机目录不入 Git，不参与状态说明）。
- codex 如需多步骤推进，通过 `collab/` 轮次目录或指定暂存状态交接，不借助未授权的提交。

## 八、定期文档梳理（回头看）

**触发**：每完成 5–6 个常规轮次，或发生重大架构调整（新机制、门禁、边界、角色变化）后，
由 dsh 发起一轮"文档梳理"轮次；用户可随时提前发起。

**目的**：消解文档与实现的不一致、内部冲突与矛盾；把新内容融入项目整体；优化文档结构
（拆分/合并/重排）与导航；确认需求完整、项目方向明确。文档不是信息堆砌，结构清晰与
内容准确同等重要。

**执行方式（两阶段，先盘点后修改）**：
1. 盘点（只读）：codex 产出双向对照表——实现→文档（每个新机制/工具/脚本/计数是否有
   权威文档描述）与文档→实现（每条现状断言是否与实现一致）；同时列出结构问题与疑似
   冲突，标出需要用户决策的重大项。
2. 修改（经确认）：dsh 审查盘点结果、用户对决策项拍板后，codex 才动笔；每处修改都要
   有"事实依据 → 文档修改"对应记录，重大结构调整单独说明理由。

**分工**：dsh 起草梳理范围与验收标准；codex 执行盘点与修改并汇报；用户对重大决策拍板。

**纪律**：
- 只改"当前描述"，不改写历史记录（历史基线、事故、旧决策、已完成 TODO 保持原样，需要
  时追加新条目）。
- 同一事实保持单一权威来源，其他文档只链接，不复制规则。
- 机械门禁（check-docs / audit-licenses / 测试计数 / 隐私扫描）全程保持 PASS；梳理轮
  同样停在提交前，按 §七 批准。
- 未决决策项写入轮次 report.md，不擅自定案。

## 九、qoder 参与与跳过

- **角色**：qoder 是方案建议与初审顾问（见 §一），无实现权、无提交权；产出写入轮次
  目录的 `qoder-notes.md`（Markdown，机械校验允许的轮次内文件）。
- **两个介入点**：
  1. 方案阶段：dsh 细化方案后、codex 实现前——qoder 读 request.md 提建议与优化，
     写入「方案建议」节；dsh 采纳或否决后定稿提示词。
  2. 初审阶段：codex 完成自测并更新 report.md 后、dsh 终审前——qoder 对照验收标准
     逐项核验并独立复核关键声明（计数/哈希/门禁/保护区/隐私），写入「初审结论」节
     （问题分级 P1/P2/P3 + 证据）；dsh 终审可采纳或推翻。
- **跳过机制**：每轮开始时由用户声明 qoder 状态（"qoder在"/"qoder不在"），dsh 记录
  于 request.md/report.md；未声明时默认跳过（流程与无 qoder 时一致）。跳过仅对本轮
  生效，下一轮可随时恢复。
- **纪律**：qoder 遵守三层边界与只读纪律（仅可写当前轮次 qoder-notes.md）；其建议
  为顾问性质，最终由 dsh 裁定、用户拍板。
- **署名规则**：轮次内 codex 与 qoder 写入的意见必须标注作者（qoder 内容在
  qoder-notes.md、codex 内容在 report.md，交叉反馈注明"codex 反馈"/"qoder 评估"）。
  署名保留至 dsh 终审通过；终审通过后，dsh 的「终审结论」节为三方共识定稿（署名
  随合并去重），各署名原文作为来源记录保留，确保信息源头可追溯。
- **临时角色交换**：用户可按轮次声明临时交换角色（如"qoder 执行、codex 初审"），
  范围限于该轮/该项目的方案制定与任务执行，dsh 始终终审；结案后身份自动恢复，
  dsh 在轮次记录中登记交换范围。
- **提交决定**：谁写的文件，谁决定提交——tracked 内容完成自检后，由作者
  （codex/qoder）在 report.md/qoder-notes.md 中写明"提交"决定及变更摘要。
  dsh 是最终评审：发现问题有权要求作者修改（返工），作者修改后重新决定提交；
  dsh 无异议时执行 git 操作并做机械门禁复核（不替代作者决定，但可拦下未解决
  的问题）；用户保持最终拍板（§一），可推翻或要求提交任何内容。
