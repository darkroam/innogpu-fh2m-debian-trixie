# 多 Agent 协作规约（dsh + codex + qoder）

> 建立于 2026-08-31 · 由用户确认生效 · 参考 clear-jlpt-n2 协作模式、按本仓库约束适配

本文是 dsh（监督）、codex（实现者）与 qoder（方案建议/初审）在本仓库协作的唯一规约。
其他文档只链接本文，不复制规则。

## 一、角色分工

| 角色 | 职责 |
|------|------|
| 用户 | 提出要求、最终拍板；确认规约变更与重大决策 |
| dsh（监督） | 把要求整理成自包含提示词与验收标准；细化方案并决定是否采纳 qoder 建议；终审 codex 成果、给出裁决与问题清单；按 §七 执行提交并复核门禁（提交决定权归作者，§九）；维护审查结论与轮次索引 |
| codex（实现者） | 按提示词落实实现，交付可运行成果；有主动性：可提出更优方案、发现问题主动汇报 |
| qoder（方案建议/初审） | 顾问角色：对 dsh 细化后的方案提建议与优化；对 codex 产出做初审（逐项核验 + 问题分级）；无实现权、无提交权，建议由 dsh 裁定、用户拍板 |

## 二、标准流程（每轮迭代 · 2026-09-21 串行交接版）

0. **串行交接总则**：同一时刻只有一人处理该轮（时分复用）；初始写者与范围由
   request/交接声明指定；前任结束时在 report.md 流水记交接行（交接对象/范围/产物
   身份），接任者核对后领取；身份与范围不明时不争抢、不超时接管；会话重置后先
   核对交接与实际文件，冲突保全双方版本交用户/dsh 指定恢复，无「最后写入者胜出」。
1. 用户向 dsh 提出要求，并声明 qoder 状态（"qoder在"/"qoder不在"，未声明默认跳过，
   见 §九）→ dsh 创建轮次 `collab/R{编号}-{YYYY-MM-DD}-{主题}/`，写入：
   - `request.md`：用户要求原文 + 完整提示词（凭据/密钥禁入），含 qoder 状态与参与
     方名单（多审核者登记 qoder-<id>）；
   - `report.md`：**流水台账模板**（append-only 共享写点；六字段：时间（含时区）|
     角色（含 id）| 动作 | 涉及文件 | 结果（含交接对象与范围）| 指针（文件@sha12
     或 文件#L行号）；动作词表：领取/交接/交付/裁定/返工/闭合；谁动手谁记一行，
     仅当轮写者可追加）；
   - 在 `collab/INDEX.md` 登记该轮（状态 `待开发`；INDEX 更新者 = 当轮写者）。
2. qoder 参与时：dsh 把细化方案交 qoder 提建议与优化（写入 qoder-notes.md 或
   qoder-notes-<id>.md「方案建议」节），dsh 采纳或否决后定稿提示词。
3. 用户将提示词交给 codex 执行；codex 如有更优方案可主动提出，经确认后执行。
4. codex 完成后填充 `codex-report.md`（做了什么/产出文件清单/验证结果/与提示词的偏差
   及原因/遗留问题；含五段式叙事与返工记录），并把 INDEX 状态更新为 `待审查`。
5. qoder 参与时：对 codex 产出做初审——对照验收标准逐项核验并独立复核关键声明，写入
   `qoder-notes*.md`「初审结论」节（问题分级 P1/P2/P3 + 证据）→ dsh 终审（机制层
   核对 + 实质层审查，见 §十三）写入 `dsh-rulings.md` → codex 返工或通过。
6. 审查通过后按本仓库 git 纪律提交（见 §七），提交说明由用户/监督定稿。

> 生效点：本结构自 2026-09-21 起对新轮生效；历史轮不追溯重构（原文与快照不变）。

## 三、提示词规范（dsh 产出）

- **自包含**：写明背景、目标、具体任务、验收标准、约束，codex 无需追问即可执行。
- **明确边界**（三层，按此分级写入提示词）：
  - **绝对禁止**（任何情况下不可修改）：本地载荷 `debs/`、`vendor/`、`build/`、
    `third_party/`，以及监督分支 `migration/supervised-source-tree`。
  - **默认保护**（默认不可修改；仅当用户在提示词中明确批准**精确路径范围**后才可改）：
    `drivers/`、`baselines/`、`binary-manifest.json`。
  - **自由范围**：其余文件，但须遵守仓库门禁（见 §六）。
- **明确交付物**：文件路径、格式、登记要求（新脚本/测试需同步 scripts/README、tests/README、
  test-strategy 与 project-tools allowlist）。
- 验收标准给足，但不限制实现路径；鼓励 codex 主动提出更优方案。

## 四、codex 主动性（实现者权限与义务）

- 收到提示词后，若认为有更优方案（工具选型、分批策略、产出结构等），可主动提出替代方案并
  说明理由，经确认后执行。
- 执行中发现提示词有误、素材缺失、或需求与实际冲突，主动汇报，不闷头硬干。
- 遇阻塞或重大偏差，及时汇报进展与影响面。
- 汇报内容须包含：做了什么、产出文件清单、验证结果、与提示词的偏差及原因、遗留问题。

## 五、合作目录存档（`collab/`）

- 位置：仓库根目录 `collab/`（英文目录名；唯一外层目录，所有轮次子目录收于其下，根目录不
  散放）。**本机私有目录**：已加入 `.gitignore`，不上传 GitHub、不参与任何公开分发。
- 结构：`collab/R{编号}-{YYYY-MM-DD}-{主题}/`，含 `request.md`（用户要求原文 + dsh 提示词）、
  `report.md`（流水台账，append-only 共享写点）、`codex-report.md`（codex 独写：交付/
  汇报/五段式叙事/返工）、`dsh-rulings.md`（dsh 独写：裁定/终审/放行）、
  `qoder-notes.md` 或 `qoder-notes-<id>.md`（审核者独写意见，多审核者一人一文件）；
  每角色只写自己的文件（空间复用），共享写点仅 report.md 流水；可选附加 `.md` 交付物；
  **轮次目录内只允许 Markdown 文件**（禁止二进制、代码快照等非约定文件，机械强制）。
- 索引：`collab/INDEX.md` 记录每轮 轮次/日期/主题/状态（状态 ∈
  待开发/开发中/待审查/通过/返工/已提交/执行中），与轮次目录按编号**双向一一对应**。
- **许可与发布边界**：`collab/` 本机私有、不入 Git，因此不是公开分发面；仍**排除出
  project-tools 候选制品**（denylist `^collab/` 防御性保留），不自动认定任何许可证；
  轮次记录中**不得出现凭据、token、私钥或机器身份**（隐私扫描覆盖 collab/），其他信息
  可按需保存；任何内容若要离开本机（同步到文档、贴出汇报等），必须先脱敏并经隐私审查。
- 机械校验：目录命名（`R{编号}-{日期}-{主题}`）、编号唯一、request.md/report.md 齐全（模板
  在创建时即生成）、INDEX 登记与合法状态、仅 Markdown 文件、INDEX 与目录按编号**双向一一对应**
  （精确匹配编号、日期与主题，R01 不误配 R010；重复行/孤立行/孤立目录/根目录或内部符号链接/
  嵌套目录均拒绝；INDEX 与隐藏 Markdown 同样纳入大小写无关的隐私扫描），由
  `tools/validate-collab.py` 执行、`scripts/check-docs.sh` 强制（collab/ 不存在时视为无轮次，
  直接通过）；fixture 见 `tests/unit/run-collab-structure-tests.sh`。

## 六、审查标准与仓库门禁（本仓库专属）

- [ ] 验收标准逐条核对通过。
- [ ] 无越界改动：§三 的绝对禁止项零改动；默认保护项仅在用户批准的精确范围内改动。
- [ ] **CI/沙箱测试入口**全部 PASS，且 test-strategy.md 计数与实际一致（"全部测试入口"指
  test-strategy.md 列出的 CI/沙箱入口，不含需真实设备/root/副作用的 runtime/授权测试；后者仅当
  任务需要且用户在提示词中批准时运行）。文档-only 任务可按风险运行相关测试 + 固定门禁。
- [ ] `python3 tools/audit-licenses.py` → `license_audit_overall=PASS` 且
  `license_release_gate=BLOCKED` 保持（发布决策 1C）。
- [ ] `bash scripts/check-docs.sh` → `RESULT: PASS_DOCS`。
- [ ] `git diff --cached --check` 干净；隐私扫描无真实用户名/hostname/凭据/token/私钥/本机
  绝对路径泄漏；涉及 shell 时 `bash -n` 与 ShellCheck（error+warning）清零。
- [ ] 新增 tracked 文件已同步 allowlist（`--write-allowlists`）与文档登记；无未登记脚本/工具。

## 七、git 纪律（本仓库与参考项目不同）

- 本仓库默认**停在提交前**：dsh 与 codex 的产出均**不得自行 commit**。
- commit / push 以作者提交决定为前提（§九 提交决定）；dsh 作为最终评审，发现
  问题可要求作者修改后再提交；dsh 执行 git 操作前做机械门禁复核并记录；用户
  最终拍板可推翻任何提交决定；**不创建 tag/Release**（发布决策 1C：当前不发布）。
- 每轮产出的报告必须明确仓库内产出的 staged / unstaged / untracked 状态与 HEAD/领先关系
  （collab/ 本机目录不入 Git，不参与状态说明）。
- codex 如需多步骤推进，通过 `collab/` 轮次目录或指定暂存状态交接，不借助未授权的提交。

## 八、定期文档梳理（回头看）

**触发**：每完成 5–6 个常规轮次，或发生重大架构调整（新机制、门禁、边界、角色变化）后，
由 dsh 发起一轮"文档梳理"轮次；用户可随时提前发起。

**目的**：消解文档与实现的不一致、内部冲突与矛盾；把新内容融入项目整体；优化文档结构
（拆分/合并/重排）与导航；确认需求完整、项目方向明确。文档不是信息堆砌，结构清晰与
内容准确同等重要。

**执行方式（两阶段，先盘点后修改）**：
1. 盘点（只读）：codex 产出双向对照表——实现→文档（每个新机制/工具/脚本/计数是否有
   权威文档描述）与文档→实现（每条现状断言是否与实现一致）；同时列出结构问题与疑似
   冲突，标出需要用户决策的重大项。
2. 修改（经确认）：dsh 审查盘点结果、用户对决策项拍板后，codex 才动笔；每处修改都要
   有"事实依据 → 文档修改"对应记录，重大结构调整单独说明理由。

**分工**：dsh 起草梳理范围与验收标准；codex 执行盘点与修改并汇报；用户对重大决策拍板。

**纪律**：
- 只改"当前描述"，不改写历史记录（历史基线、事故、旧决策、已完成 TODO 保持原样，需要
  时追加新条目）。
- 同一事实保持单一权威来源，其他文档只链接，不复制规则。
- 机械门禁（check-docs / audit-licenses / 测试计数 / 隐私扫描）全程保持 PASS；梳理轮
  同样停在提交前，按 §七 批准。
- 未决决策项写入轮次 report.md，不擅自定案。

## 九、qoder 参与与跳过

- **角色**：qoder 是方案建议与初审顾问（见 §一），无实现权、无提交权、**不修改任何
  项目文件**；产出写入轮次目录的 `qoder-notes.md`（默认）或 `qoder-notes-<id>.md`
  （多审核者时一人一文件，<id> 在 request 参与方名单登记；顺序由 report.md 流水记录承载）。
- **两个介入点**：
  1. 方案阶段：dsh 细化方案后、codex 实现前——qoder 读 request.md 提建议与优化，
     写入「方案建议」节；dsh 采纳或否决后定稿提示词。
  2. 初审阶段：codex 完成自测并更新 report.md 后、dsh 终审前——qoder 对照验收标准
     逐项核验并独立复核关键声明（计数/哈希/门禁/保护区/隐私），写入「初审结论」节
     （问题分级 P1/P2/P3 + 证据）；dsh 终审可采纳或推翻。
- **跳过机制**：每轮开始时由用户声明 qoder 状态（"qoder在"/"qoder不在"），dsh 记录
  于 request.md/report.md；未声明时默认跳过（流程与无 qoder 时一致）。跳过仅对本轮
  生效，下一轮可随时恢复。
- **纪律**：qoder 遵守三层边界与只读纪律（仅可写当前轮次 qoder-notes.md）；其建议
  为顾问性质，最终由 dsh 裁定、用户拍板。
- **署名规则**：轮次内 codex 与 qoder 写入的意见必须标注作者（qoder 内容在
  qoder-notes.md、codex 内容在 report.md，交叉反馈注明"codex 反馈"/"qoder 评估"）。
  署名保留至 dsh 终审通过；终审通过后，dsh 的「终审结论」节为三方共识定稿（署名
  随合并去重），各署名原文作为来源记录保留，确保信息源头可追溯。
- **临时角色交换**：用户可按轮次声明临时交换角色（如"qoder 执行、codex 初审"），
  范围限于该轮/该项目的方案制定与任务执行，dsh 始终终审；结案后身份自动恢复，
  dsh 在轮次记录中登记交换范围。
- **提交决定**：谁写的文件，谁决定提交——tracked 内容完成自检后，由作者
  （codex/qoder）在 report.md/qoder-notes.md 中写明"提交"决定及变更摘要。
  dsh 是最终评审：发现问题有权要求作者修改（返工），作者修改后重新决定提交；
  dsh 无异议时执行 git 操作并做机械门禁复核（不替代作者决定，但可拦下未解决
  的问题）；用户保持最终拍板（§一），可推翻或要求提交任何内容。

## 十一、双轨变更纪律（两条腿）

- **目标**：把未来「更换基座」的成本从考古式逐文件归纳降为「全链 patch 重放 + 适配」。用户 2026-09-10 裁定，dsh 草拟确认。
- **规则**：凡进入发布包（当前 5.0.0-iN fantgpu 血缘）的源树语义改动，必须双轨存在：
  1. **腿 A（直接修改）**：在工作树/编排树上直接修改（正常开发路径）；
  2. **腿 B（patch 记录）**：同一改动同时落档为 `patches/030-NNN.{patch,meta.json}`（N 从 030 起续编，相对上一链基，-p1 --fuzz=0 可重放），meta 含 4 目评审、before/after tree hash、draft→verified 生命周期、rollback 字段与台账引用；台账（`030-mapping-table.md` 或 5.x 变更台账）同步登记来源、语义与验证状态。
- **印证门禁**：发布前 O_stage 物化树 hash 必须等于「F0 快照 + 全链 030-NNN 重放」树 hash；不一致即阻塞发布（缺失腿 B 的改动 = 返工）。
- **基座更换流程（未来）**：新 vendor 基座 = F0′ → O-4′ 锁定 → 全链 patch 逐项重放 + 适配（复用既有 4 目评审语义裁决，仅重适配上下文/命名）→ O_stage′；禁止回到考古式逐文件归纳。
- **例外**：纯构建/打包/元数据配置（非源树语义）可不产 patch，但必须记入对应版本 meta.json 并说明。
- **监督**：dsh 终审按本条款核验双轨闭合；codex/qoder 的「提交」决定必须声明腿 B 状态。

## 十三、协作机制要点（十项 · 2026-09-21 用户裁定）

1. **哈希 = 文件标准名字**：文件名+哈希构成精确引用，仅标识不判定；不替代内容审查。
2. **终审/抽验两层制**：机制层（确认读的是哪一个文件）+ 实质层（确认内容正确），对
   dsh 终审与 qoder 抽验同等适用；dsh 直接修改产物 = 临时身份互换，须经 codex
   独立交叉检查确认，不得沿用修改前的通过结论。
3. **错误即资产两层制**：Tier A 逐字（哈希/裁决值/冻结原文/命令回包/因果关键句/
   裁定原文）；Tier B 三要素（事实+处置+教训）；禁止「已修复」类措辞覆盖冻结状态。
4. **一文件一写者 + 写锁 = 流水行自证**：见 §二 串行交接总则。
5. **小样本定格式 → 批量**：格式先过审再批量执行，避免格式返工。
6. **设计阶段只产出文档与获准的只读事实采集**：patch/构建/安装/运行证据须在明确
   放行后生成；「只读」不天然无副作用（debugfs 读取/探针可触发驱动、pstore 复制
   产生新归档）——设计批须列明允许读取与输出位置。
7. **修稿全量重出哈希**：任何交付物修改后重新报送该批完整清单并标变更项；不扩展为
   全仓重算、不回填历史旧 SHA。
8. **批约定与门禁覆盖声明**：无人值守构建期间不得重启主机等批约定入 maintenance-
   policy；交付注明检查对象与覆盖边界（untracked 新文件不被 audit/tracked 面扫描；
   check-docs 隐私扫描用 --no-ignore 覆盖 untracked docs/collab），dsh commit-time
   纳入后重跑四门禁。
9. **历史命令不构成执行授权**：文档中的历史命令只作证据引用，不构成安装/挂起/构建/
   回退授权。
10. **协作规则单一权威**：协作/交接/授权全归本文件；其他文档只链接不复制；Tier A/
    快照副本与门禁必要摘要不在去重范围。

- **codex 独立执行特例（用户 2026-09-21 裁定）**：codex 是必须的最小工作单元；无
  dsh/qoder 在场时，可按用户直接要求独立完成任务并自管文档——受用户已授权范围约束，
  不自动解除专项冻结或替代明确要求的放行。
- **dsh 扩展常态**：dsh 是常态必选扩展（用户让渡部分权利）：指导/检查 codex 工作、
  确认推进，可参与文件编写；直接修改 codex 工作按第 2 项处理。

## 十二、文档优化迭代流程（四轮 · 2026-09-19 三方合并版）

### 12.1 目标与总则

- **目标**：多轮工作后周期性把文档收敛为「与实现一致、结构清晰、便于后续检查」的形态。四轮：1 内容对齐 → 2 结构调整 → 3 二次对齐 → 4 收尾。
- **冻结**：迭代期间不改任何实现（源码/补丁链/脚本/构建产物/证据）；不可变区只读引用不重写。
- **不可变区清单**：docs/planning/evidence/**、patches/**、.runtime-archive/**（本机唯一副本，不入 Git，引用须注明）、baselines/**（运行结果目录）、build/**、debs/**、vendor/**、third_party/**、LICENSES/**、THIRD_PARTY_NOTICES.md、allowlist 两件、git tags（迭代期禁打/禁移）、collab 原文快照区；本规约除本节按三方合并更新外，其余条款只读。
- **门禁**：每轮结束 git diff --check + 四门禁；allowlist 由 dsh commit-time 重生成；tracked 文档每轮结束一个提交。

### 12.2 快照与原文保留（前置硬规则）

- 改写任何 collab 轮次前，先把该轮全部原文快照（tar + 逐文件 SHA-256 清单）存入 .runtime-archive/r17-docs/archive-originals/<轮次>/；快照须验证可解包且逐文件 SHA 一致；该区为既有归档之外的新增快照，既有归档仍只读；R17 轮目录只放 Markdown 索引，不嵌套目录。
- **原文不改写**：request/report/qoder-notes 原样保留；五段式叙事写为新增 narrative.md（阅读版），由 INDEX/首行引导；qoder-notes 永不改写、不并入。
- **术语**：三基线 deb 统一称「基线代际」，与 baselines/ 运行结果目录区分。定稿名称：代一「legacy patched 阶段（3.3.3.42-patched-N；原包解包+补丁叠加，p27 已属 Deepin）」、代二「deepin 4.0.x 源码树迁移线」、代三「fantgpu 5.0.0-iN（当前诊断线）」；入口见 [glossary](glossary.md)，代际划分不等同于 Git 祖先链。

### 12.3 错误资产两层制（错误即资产）

- **Tier A 逐字保留**：哈希/SHA/裁决值、冻结条款原文、命令与关键回包行、事故因果关键句、dsh 裁定原文行（可截断，须留指针）。
- **Tier B 等价浓缩三要素缺一不可**：事实（时间/对象/数值/环境）+ 处置（怎么修/为何停批/是否回退）+ 教训句。
- **核对表字段**：事件ID | 类别 | 原文位置（快照文件+行） | 改写稿位置 | Tier | 保留要点 | 验证方式 | 结果。qoder 抽验：Tier A 逐字 ≥30% + 全量 hex 串复算。
- **哈希防漂移（可脚本化）**：改写稿全部 hex 串逐一验证——完整文件 SHA 对实物复算；提交号查存在与所指内容；短哈希查前缀与唯一性；历史产物缺失时保留引用并注明「无法复算」，不得为过门禁补造结果；禁止排版性「修正」任何字符。
- **哈希语义（用户 2026-09-20 裁定，禁止唯哈希论）**：哈希就是文件的**标准名字**——「文件名 + 哈希」构成一个可读、可用文件的精确引用，让你知道用的是哪一个文件，仅此而已。它不是内容判定、不是质量证明、不替代阅读；核对通过后审查义务即转移到实质通读；修改后产生新哈希（新名字）供下游引用。
- **冻结措辞禁令**：禁止以「已修复/已通过」类措辞覆盖 R5=FAIL、U1/U2、validation-results、未打 tag。

### 12.4 每轮 DoD 与轮次闭合单

- DoD 每条必须配「检查物/判定方法/结果」三列；每轮产出固定「轮次闭合单」（DoD 逐项 + 快照清单 + 门禁输出摘要 + 台账链接 + 提交号 + qoder 复核结论）。
- **R1**：inventory 全项带证据指针打勾；错误资产核对表 100% 可定位；实现对齐抽验每区域 ≥5 项或 ≥10% 且哈希/路径/命令三类全查；快照清单存在；四门禁。
- **R2**：三基线代际文档齐（每篇「本代工作 + 与上一代差异」+ 基线事实表逐项溯源；不可证明项标 UNVERIFIED）；旧文档归位/跳转台账 100%；docs/ 相对路径存在性检查；四门禁。
- **R3**：通读清单枚举到文件；每文件 reviewed_by/date/内容 SHA；术语对 glossary 全表检索对照。
- **R4**：每文件 diff ≤20 行、无章节增删、无事实性变更；跳回台账为空或全闭环。

### 12.5 跳回机制

- 台账字段：事件 | 发现时间 | 触发条 | 影响范围 | 处理 | 闭环日期 | 复核人。
- 六条触发：① 事实性错误；② 错误资产不可定位或 Tier A 不符；③ 失效链接/路径不存在/术语冲突；④ 单文件超小改阈值；⑤ 三基线文档与事实表不一致；⑥ 冻结语句漂移。命中 → 跳回 R3 重做对应范围；纯链接修正可不重启整轮。

### 12.6 基线事实表（R2 前置）

- 每代记录：起止事件与日期 / tag+commit（或「未打 tag」）/ 代表 deb（路径+SHA）/ 载体与 ABI 特征 / 回滚物指向。日期分列「目标提交日期 / tag 创建日期」；0.5 目标提交为 2026-05-28，轻量 tag 创建日期不可证；patched-27 目标提交为 2026-08-20，tag 创建于 08-21；deepin-4.0.2-i3 两日期均为 09-09。无 patched-18/19/20 tag；fantgpu-5.0.0-iN 未打；已核实 0.5 非 patched-27 祖先，仅归于同一文档阶段；回滚 deb 177133ee… 在位。不可证项标 UNVERIFIED，路径缺失不得外推为本机实物缺失。
- **发布与安装状态分开**：5.0.0-i6 是当前诊断线，不得因文档主线化而描述成已验收发布版。

### 12.7 执行顺序与切片

- R01 三件套样本（五段式 narrative + TEMPLATE-round-narrative.md + 错误资产核对表示范）→ qoder 定调三问 → dsh 确认 → R02–R15 批量 → R16 四切片最后（基座评估/030 链/R5 悬案/诊断内核两轮）。
- 一文件一写者；切片间不得并行同一文件；每片改动 ≤3000 行 + 独立复核；时间盒防大爆炸式评审。
- check-docs 对历史版本的固定措辞要求与「当前状态」更新冲突时：登记并另行裁决，不得保留失实描述换门禁通过；文档中的命令不是执行授权（挂起/安装/恢复命令尤其如此）。
- **修稿全量重出哈希**：任何设计/patch/脚本改动都使既有评审哈希失效，必须全量重算并重新初审（§十三第 7 项同一口径）。
- incidents 提升：5.0.0 线事故（i4 Oops/dev_rsrc ABI、脚本缺陷重蹈、越界产物）提升为 docs/incidents 文档；其余以指针留叙事。
